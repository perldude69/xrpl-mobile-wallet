Abstract

This report presents the findings of a security audit of XRPL Mobile Wallet (xrpl_mobile_wallet, Android application id info.richlist.wallet). The audit covered key derivation and entropy, PIN and lock gating, Android Keystore usage, payment construction and fee handling, USB Ledger signing, the address-only background watcher, custom JSON-RPC/WSS endpoints, encrypted public-list export, and the Android packaging surface (backup, exported components, release signing).

The core crypto path is clean and, in the important cases, verified rather than only asserted: mnemonic derivation is pinned by golden vectors against xrpl.js Wallet.fromMnemonic, create delegates to import, OS CSPRNG is never replaced by the dice ritual, and the watcher isolate does not import secret-bearing modules. A prior review (findings XRW-01 through XRW-07) plus a follow-up pass (XRW-08 through XRW-14) led to hardening that this re-audit confirmed in source and, for packaging and screen security, on a physical Pixel 8 Pro.

One High finding remains open and is confirmed on the installed APK: the release build is signed CN=Android Debug (XRW-01). XRW-15, XRW-16, XRW-17, XRW-18, and XRW-20 were remediated in this pass and re-checked in source (and XRW-16 on-device). Remaining items are Informational. No Critical findings were identified.

Overview

The product is a personal, sideloadable Android wallet. Secrets live in the UI process via KeyVault / PinService (Android Keystore through flutter_secure_storage). Metadata lives in Drift / SQLite. A foreground service watches public classic addresses over WSS and never holds keys.

Scope for this pass:

  • lib/ — domain, data, state, and UI
  • android/app/ — Gradle signing, manifest, MainActivity FLAG_SECURE channel
  • packages/ledger_usb_plus/ — vendored USB plugin (path dependency)
  • test/ — golden derivation, PIN KDF migration, export KDF clamps, fee and destination-policy validators
  • Release APK installed on Pixel 8 Pro (husky, Android 17 / API 37) — signing, backup, merged manifest, FLAG_SECURE, exported components

Out of scope unless they affect Android sideload security: iOS release polish, Play App Signing (explicitly deferred by the maintainer), live mainnet send, and USB Ledger hardware (none attached).

Tree under review: git 193f222 (feat: add RLUSD trust line for signing and Ledger wallets) plus unpublished hardening on the working tree (PIN PBKDF2, backup off, fee clamp, dest-tag checks, re-auth, FLAG_SECURE on PIN surfaces, export iter clamp, resetOnError: false, watcher exported=false).

Findings

XRW-01 Release signed with the shared Android debug key

High

Description. android/app/build.gradle.kts still assigns the release build type the debug signing config. Because this app is sideloaded and does not use Play App Signing, Android treats any APK signed with the same debug certificate as a legitimate upgrade of info.richlist.wallet.

Impact. Anyone who can induce the user to install a same-signature APK (sideload, “update”, malicious mirror) gets in-place access to the existing Keystore entries and the SQLite database. That is full key theft for software wallets on that device. Ledger-only wallets are not drained this way (keys never leave the device), but watch metadata and custom endpoint URLs are still inherited. 

buildTypes {
    release {
        // TODO: Add your own signing config for the release build.
        signingConfig = signingConfigs.getByName("debug")
    }
}

Device verification (Pixel 8 Pro, 03 Sep 2026). Release APK app-release.apk (85.7 MB) was installed with adb install -r over the existing package (in-place upgrade succeeded — same debug cert). apksigner verify --print-certs: 

Signer #1 certificate DN: C=US, O=Android, CN=Android Debug
SHA-256: 4f7c44706efc01e6c1a72ab86c07c5f202839437adce8a179bd0ff03cf198951
SHA-1:   bd0c7f7b1d7814812ea35aee591499e5986c1044

PackageManager signatures=[206b800e], apkSigningVersion=2. The installed binary is the shared Android debug key. Finding stands.

Resolution. Generate a unique upload keystore, point signingConfig at it, and never ship another APK under the debug cert. The maintainer has deferred this to App Store / Play signing. After the cutover, repeat apksigner verify --print-certs and confirm the DN is no longer CN=Android Debug. Existing installs will need a one-time uninstall or a migration APK signed with both certs — Android will not upgrade debug→release otherwise.

XRW-02 No persistent PIN throttling

Informational

Description. Failed unlock attempts are counted only in UnlockScreen._failedAttempts. The counter is in-memory, resets to zero after the third failure (when the Zerpland decoy opens and no game PIN is set), and does not survive process death. There is no backoff and no lockout. Minimum PIN length is 6 digits.

Impact. An attacker with the unlocked phone hardware can try the 1,000,000 6-digit space without a durable delay. The product mitigation is the 3-fail decoy (and the optional game PIN, which disables that decoy and instead opens Zerpland only on the second PIN). The maintainer accepted this risk.

Online guessing is the real PIN attack. The PIN hash is not a KEK (see XRW-19): an attacker who can read Keystore already has the seeds. 

int _failedAttempts = 0;
// …
if (useFailDecoy && _failedAttempts >= 3) {
  _failedAttempts = 0;
  await _openGame();
}

Resolution. None required for this pass. A later hardening could persist a failure counter and add exponential backoff without removing the decoy.

XRW-19 PIN is an application lock, not a KEK

Informational

Description. Wallet secrets and PIN verifiers share FlutterSecureStorage with AndroidOptions(resetOnError: false). The PIN is now PBKDF2-SHA256 at 120,000 iterations with a 16-byte salt (legacy single-round SHA-256 hashes upgrade on the next successful unlock). The PIN is not used to wrap the seed. Keystore AES-GCM (RSA-OAEP wrapped) is the at-rest control; the PIN only gates the Flutter UI (and spend re-auth).

Impact. Correct, and worth stating so the KDF upgrade is not mistaken for seed encryption. A compromised UI process, or Keystore access on an unlocked device, does not need the PIN to read wallet_secret_*. Hardware-backed setUserAuthenticationRequired is not enabled (biometrics are an optional UI unlock via local_auth, flagged in SharedPreferences).

Resolution. No change required for the current threat model. If the PIN should survive a stolen-but-unlocked-device story, wrap vault values with a PIN-derived key or enable Keystore user authentication. That is a product decision, not a bug in the current split.

XRW-15 Review fee is a snapshot; sign-time fee can differ

Resolved

Description. The review step displayed XrplRpcClient.fetchMinimumFeeDrops() (fee RPC, XrplFeeType.minimum). Signing later called XRPHelper.autoFill, which fetched the fee again and wrote it onto the transaction. The displayed value was therefore not the number that would be signed. A clamp of 0.1 XRP (AppConfig.maxFeeDrops = 100000) applied at sign time for both software and Ledger paths, so a malicious node could not push the 20 XRP xrpl_dart default.

Impact. Between review and confirm, open-ledger fee could move. The user might sign a higher fee than the one they just read, up to the 0.1 XRP cap, without a second prompt. Direct theft of a large amount via fee was no longer possible. 

// review
final drops = await rpc.fetchMinimumFeeDrops();

// later, on confirm
await XRPHelper.autoFill(rpc, transaction);
final feeError = PaymentValidators.validateFeeDrops(transaction.fee?.toString());
if (feeError != null) throw ArgumentError(feeError);

Resolution implemented. Review now stores the fetched minimum fee. PaymentService sign paths take expectedFeeDrops and refuse to sign unless autoFill’s fee is identical (PaymentValidators.reviewedFeeMatches). A changed fee sends the user back to Review.

XRW-16 Plugin Boot / Watchdog receivers remain exported

Resolved

Description. The app manifest set the watcher foreground service android:exported="false" via tools:replace. The flutter_background_service_android plugin still shipped WatchdogReceiver and BootReceiver with exported="true". Those components were merged into the final APK unless overridden.

Impact. Other apps on the device could send explicit broadcasts to the watchdog / boot receivers. The isolate still holds no secrets (address book is public addresses only), so this was start/stop of notifications rather than key theft. Combined with RECEIVE_BOOT_COMPLETED, a hostile app could nag the watcher to start. 

<!-- plugin AndroidManifest -->
<receiver android:name=".WatchdogReceiver" android:exported="true" />
<receiver android:name=".BootReceiver" android:exported="true">
  <intent-filter>
    <action android:name="android.intent.action.BOOT_COMPLETED"/>
  </intent-filter>
</receiver>

Resolution implemented. App manifest now overrides both plugin receivers with android:exported="false" and tools:replace="android:exported". Merged release APK (aapt): WatchdogReceiver and BootReceiver exported=0x0. Re-installed on Pixel 8 Pro 2026-09-03 21:40. System still delivers BOOT_COMPLETED to the non-exported BootReceiver (protected broadcast). Third-party apps cannot target them.

XRW-17 Preset-destination send skips dest-tag policy

Resolved

Description. Ordinary send loaded account_info flags at the destination step and refused when lsfRequireDestTag is set and the tag is empty, or when lsfDisallowXRP is set for an XRP payment. The Settings coffee flow constructed SendScreen with presetDestination: AppConfig.coffeeAddress, which jumped straight to the amount step and never ran fetchDestinationPolicy.

Impact. The hardcoded coffee address is a normal funded account without dest-tag requirement, so funds were not at risk on that path. Any future reuse of presetDestination (deep links, address-book shortcuts) would have inherited the skip. 

if (_hasPresetDestination) {
  _destinationController.text = widget.presetDestination!.trim();
  _selected = const LedgerBalance(currency: 'XRP', value: '0');
  _step = _SendStep.amount; // dest-tag / disallowXRP never checked
}

Resolution implemented. Preset destinations load fetchDestinationPolicy on open and again before leaving the amount step. Coffee send now hits the same dest-tag / lsfDisallowXRP gate as a normal payment.

XRW-18 Available-balance check ignores fee and reserve

Resolved

Description. The amount step compared the send amount to the cached XRP balance only. It did not subtract the network fee, the 1 XRP account-create reserve when the destination is unfunded, or owner-reserve for remaining objects. The destination-policy fetch already distinguished unfunded accounts (DestinationAccountPolicy.unfunded) but that result was not threaded into the amount check.

Impact. Users could pass local validation and then fail on ledger (tecUNFUNDED_PAYMENT / insufficient reserve). This was not theft; it was a failed submit after PIN and, for Ledger, after a device approval. Annoyance and a wasted fee if the engine claimed one.

Resolution implemented. PaymentValidators.validateXrpSpendable requires amount + fee ≤ available XRP, and at least AppConfig.accountCreateReserveDrops (1 XRP) when the destination is unfunded. Enforced before Review.

XRW-20 Encrypted export file left in app documents after share

Resolved

Description. List export wrote password-encrypted AES-256-GCM JSON (names and addresses only; no seeds) under getApplicationDocumentsDirectory() and handed the path to share_plus. The file was not deleted afterwards. Decrypt already rejected attacker-controlled iter outside 120,000–600,000 and checks salt/nonce/mac/ct lengths (prior XRW-06).

Impact. Ciphertext of the public address book remained on disk. Keys are not in the file. Auto Backup is disabled (XRW-04), so the leftover file did not go to Google Drive. A weak export password still brute-forces at the clamped KDF.

Resolution implemented. Export writes to getTemporaryDirectory() and deletes the file in finally after share returns (success or failure).

3 Audit structure

Each subsection records what was reviewed and whether a finding was raised. Where the implementation matched the intended security model, that is stated explicitly.

3.1 Key derivation and entropy

New wallets always draw 32 bytes from Random.secure. EntropyMixer.mix domain-separates xrpl-mobile-wallet/v1/entropy and SHA-256-mixes OS bytes with the dice/word ritual. The ritual cannot replace OS entropy.

BIP39 import uses path m/44'/144'/0'/0/0 and secp256k1 only, matching xrpl.js Wallet.fromMnemonic. WalletGenerator.createFromMnemonic delegates to WalletImporter.importMnemonic, so create and import cannot drift. Family seeds use XRPPrivateKey.fromSeed (often ed25519) on a separate path. Signing tries secp first and falls back to ed25519 only when expectedAddress matches a legacy mis-import.

Golden tests still pin:

  • abandon × 11 + about → rHsMGQEkVNJmpGWs8XUBoTBiAAbwxZN5v3
  • genesis family seed snoPBrXtMeMyMHUVTgbuqAfg1SUTb → rHb9CJAWyB4rj91VRWn96DkukG4bwdtyTh

BIP39 passphrases (25th word) are not supported. That is a compatibility limitation, not a vulnerability: a passphrase wallet imported without the passphrase derives a different address and is rejected if used for attach-keys against a known address.

No new findings in this area.

3.2 PIN, game PIN, biometrics, auto-lock

Unlock classifies wallet PIN first, then optional game PIN. Game PIN must differ from wallet PIN at set time. Spend, TrustSet, wipe, delete, and enabling biometrics re-prompt the wallet PIN. Biometrics use biometricOnly: true (no fallback to the device credential). The biometrics-enabled flag remains in SharedPreferences; it does not unlock Keystore by itself.

Auto-lock starts the 90-second timer on paused or inactive. A long USB permission dialog can therefore lock the session under an in-flight Ledger send; the async submit still runs until mounted checks fire. Not raised as a finding; worth knowing when testing Ledger.

Findings: XRW-02 (accepted), XRW-19 (by design).

3.3 Secret storage and Android backup

kAppSecureStorage is the single FlutterSecureStorage used by KeyVault and PinService, with resetOnError: false. A decryption error now surfaces rather than deleting the vault. SQLite (xrpl_wallet.sqlite in app documents) still holds addresses, labels, balances, and tx cache in the clear; it has no secret columns. With allowBackup="false" that database is not sent to Google Drive.

The watcher address book is JSON {address, label, network, wss, enabled} only. watcherOnStart does not import key_vault.dart or pin_service.dart.

No open findings in this area (XRW-20 tempfile deleted after share).

3.4 Payment construction, fees, destination policy

Software payments: build → autoFill → fee clamp → toSigningBlobBytes → local sign → submit. Secrets are method arguments from KeyVault at the call site and nulled in finally.

Destination policy uses account_flags.requireDestinationTag / disallowIncomingXRP when the node provides decoded flags, otherwise the account_data.Flags bits 0x00020000 / 0x00080000. Unfunded destinations (actNotFound) are allowed (account create). The policy is only as honest as the selected RPC node; a user-added malicious node can lie about flags. That is the same trust the user already grants for fee and balances, now bounded on fee.

XRW-15, XRW-17, and XRW-18 are resolved in this pass.

3.5 Ledger USB

Path m/44'/144'/index'/0/0 secp256k1. The phone never stores Ledger private keys. Before sign, the app compares the device address to the wallet row and aborts on mismatch. The device is given transaction.toTransactionBlobBytes() (STObject with SigningPubKey, no TxnSignature), not toSigningBlobBytes (STX\\0 software digest) — the latter caused SW 0x680b in earlier work.

APDU logging is kDebugMode only and no longer dumps hex payloads. USB permission is UsbManager.requestPermission plus USB_DEVICE_ATTACHED / usb_device_filter.xml (Ledger vendor 0x2c97), not a runtime permission.

No physical Ledger was available for this pass. The STObject vs STX\\0 choice and address check were confirmed in source and unit tests for APDU helpers.

No open findings in this area.

3.6 Watcher isolate and notifications

The FGS is dataSync, address-only. Status notifications show host, never a URL query string. Activity notifications parse validated stream frames; oracle TrustSet quotes from rXUMMaPpZqPutoRszR29jtC8amWq3APkx update a local rate cache and are not shown as wallet activity.

A malicious custom WSS can inject fake “validated” events and poison the USD display or spam notifications. It cannot sign. Acceptable for a user-chosen node.

XRW-16 plugin receivers are now exported=false in the merged APK (confirmed on device).

3.7 Network endpoints

Mainnet catalog failover: xrplcluster → mainnet.xrpl-rpc.com (Ankr). Testnet is fixed Ripple altnet. Custom URLs must be https:// or wss://; cleartext is rejected. Status UI uses EndpointUrl.hostOf. There is no certificate pinning; the user is trusting system CAs plus whatever node they added. No network_security_config is required for that model on current targetSdk (cleartext already blocked).

No additional findings.

3.8 Android packaging

Permissions: Internet, camera (QR, optional), notifications, FGS dataSync, wake lock, boot completed. No contacts, storage, or location. MainActivity is exported (launcher + USB attach). Watcher service is not. Debug signing remains XRW-01 and was confirmed on the installed release APK (CN=Android Debug).

FLAG_SECURE is toggled from Dart via a method channel in MainActivity.kt, now refcounted so a PIN dialog over Send does not clear the flag on dialog dispose.

3.9 Export / import of the public list

Envelope is generic JSON (v, kdf, iter, salt, nonce, mac, ct) with no product branding. Plaintext is AES-256-GCM of {items:[{n,a}]}. Import adds missing addresses as watch-only. Password minimum is 6 characters — consistent with PIN policy, weak if the file leaks, but the file is not a seed backup.

XRW-20 tempfile is deleted after share.

3.10 Screen security and logging

Create, import, attach-keys, send, unlock, setup PIN, and PIN/password dialogs enable FLAG_SECURE. Secret TextEditingControllers are overwritten on dispose. Mnemonic clipboard copy warns and clears after 60 seconds if unchanged. lib/ has no print; Ledger debugPrint is debug-only and payload-free.

No open findings in this area. On-device: see § Device verification.

Limitations

Packaging, backup, exported-component, and FLAG_SECURE claims that previously depended on source-only reasoning have been checked on a Pixel 8 Pro running the release APK. Still not covered:

  • No USB Ledger was attached, so APDU exchange and on-device fee display were not live-tested.
  • No mainnet/testnet payment was submitted; fee-match and spendable checks are unit-tested.
  • No second-party APK was built to demonstrate the debug-key upgrade attack end-to-end; the cert identity plus successful adb install -r of a same-signature rebuild is the evidence.

Unit tests covering derivation goldens, PIN migration, export iter rejection, fee clamp / reviewed-fee match, destination policy, spendable XRP, and unique addresses were run as part of this pass (flutter analyze clean, flutter test 163 passed).
