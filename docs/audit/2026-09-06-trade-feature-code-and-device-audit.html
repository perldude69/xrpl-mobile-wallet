XRPL Mobile Wallet — Trade Feature Code & Device Audit

06 September 2026 Independent automated pass (Claude Code) Package info.richlist.wallet · versionName 2.0.0 (versionCode 4)

A fresh pass over the working tree as it stands on branch main at commit 7d3acbd plus ~3,000 lines of uncommitted change (a new XRPL Trade feature, testnet faucet helper, per-network wallet scoping, schema v4, and a new default RPC endpoint), and over the release APK built from that tree and installed on the attached Pixel 8 Pro 38181FDJG00F43. The code was reviewed on its own merits; prior audit rounds (XRW-01 … XRW-25) were not re-litigated. Finding IDs continue the XRW space.

Abstract

0 High 0 Medium 3 Low 3 Informational

The new Trade flow keeps the wallet's core secret-handling discipline: the signing key is read only after a verified wallet PIN, held in a local variable, and pushed through the same guarded sign/submit path as payments (fee cap, address check). No secret disclosure — on screen, on disk, or in logs — was found.

What the pass did surface is a cluster of polish and safety-parity gaps around a money-moving feature that ships with no tests: raw library exception text is rendered in the new UI again (regression of the closed XRW-25), a maintainer-operated host is now the default mainnet RPC and the default submit endpoint for signed offers (XRW-27), the Trade action is offered to Ledger wallets it cannot actually sign for (XRW-30), and the pre-sign review omits the network fee and reserve impact the feature's own design document requires (XRW-29). None are exploitable as written.

Methodology

  • Full read of the uncommitted delta: git diff plus the new files lib/ui/trade/trade_dashboard_screen.dart, lib/data/xrpl_rpc/testnet_faucet_service.dart, the trade execution plan (since folded into docs/design/2026-09-06-consolidated-plan.md), tool/testnet_trade_trial.py.
  • Focus surfaces: the new sign/submit entry point (PaymentService.signAndSubmitTransaction → _signAndSubmit), OfferCreate / OfferCancel construction and amount conversion, PIN-gating order relative to key reads and DB writes, exception handling and what reaches the screen and the Drift DB, the new rpc.rich-list.info catalog entry, per-network wallet filtering in WalletListController.reload, schema v3 → v4 migration, and the testnet faucet POST.
  • flutter pub get, flutter analyze (clean), flutter test (168/168).
  • Release build via tool/build_release.sh (--obfuscate --split-debug-info=build/symbols/android); apksigner / aapt2 inspection; ELF section scan of lib/arm64-v8a/libapp.so; native string scan for secret material.

Findings

XRW-26Raw exception text rendered in the new Trade UI

Low CWE-209 / MASVS-CODE

Location. lib/ui/trade/trade_dashboard_screen.dart: line 246 SnackBar(... Text('XRPL rejected submit: ${e.message}')) (RPCError), line 280 Text(e.message?.toString() ?? 'Limit order submission failed') (ArgumentError), line 296 SnackBar(content: Text(e.message)) (BaseXRPLPluginException).

Description. The 2026-09-05 XRW-25 remediation removed all e.toString() / e.message passthrough from lib/ui and routed unexpected failures through userFacingError(). The new Trade screen reintroduces the pattern in three snackbars. As with XRW-25, the dependencies actually invoked here (xrpl_dart, blockchain_utils) throw fixed strings that never quote a secret, and the signing key never reaches these catch arms, so there is no disclosure today. The finding is the reopened channel: a future dependency bump could surface richer text verbatim on a screen that may not be FLAG_SECURE-protected.

Recommendation. Map to fixed messages the way the rest of lib/ui now does — reuse userFacingError() and the PaymentOperationException.stage codes the submit path already produces. The generic catch (e) arm at line 310 is already correct; make the typed arms match it.

XRW-27Maintainer-operated host is the new default mainnet RPC and offer-submit endpoint

Low CWE-668 / privacy · integrity

Location. lib/data/endpoints/endpoint_preferences.dart:116–122 — rpc.rich-list.info is inserted as the first entry of mainnetHttpCatalog, ahead of xrplcluster.com.

Description. Selected endpoint IDs default to the catalog in order (an empty selection "falls back to the full catalog"), so on a default install the first working entry — now rpc.rich-list.info — serves every mainnet JSON-RPC call: account_info, account_lines, account_tx, account_offers, and submit. Two consequences:

  • Privacy. Every wallet address a user holds, plus its balance and history polling, is concentrated at one maintainer-run host by default rather than spread across a public cluster.
  • Submit-path position. This build adds OfferCreate / OfferCancel submission. An RPC that receives a signed offer blob before it is broadcast is positioned to delay, drop, or front-run it. The blob is already signed so its contents cannot be altered undetected, but ordering and disclosure are in the endpoint's hands.

The in-tree catalogs now disagree: lib/config/network_id.dart still lists xrplcluster.com first for both HTTP and WSS, while endpoint_preferences.dart leads with rpc.rich-list.info (HTTP only — it is absent from the WSS catalog, so the watcher is unaffected).

Existing mitigations. TLS is enforced (EndpointUrl.validate rejects non-https); the endpoint is user-disableable and reorderable in Settings; status UI shows host only.

Recommendation. Keep a neutral public cluster as the default first entry and offer rpc.rich-list.info as a non-default selectable option; reconcile the two catalogs; and state in docs/privacy/privacy.md and/or in-app that the endpoint is maintainer-operated.

XRW-30Trade is offered for Ledger wallets but can never sign for them

Low CWE-451 / misleading UI

Location. lib/ui/wallets/detail/wallet_detail_screen.dart:399–411 (Trade button shown unconditionally) and lib/ui/trade/trade_dashboard_screen.dart (_cancel, _createLimitOrder).

Description. The Trade screen keys its "can sign" branches off WalletAccount.canSign, which is true for a Ledger wallet (useLedger). But both signing paths call keyVaultProvider.readSecret(account.id) and the software PaymentService.signAndSubmitTransaction only — there is no LedgerXrpDevice path. For a Ledger wallet readSecret returns null, yielding StateError('No signing key') and a generic failure snackbar after the user has been walked through draft → review → PIN. The feature's design document explicitly requires each Trade transaction to be signed on the device for Ledger wallets.

Recommendation. Until the on-device path exists, gate Trade signing to WalletKind.signing (treat Ledger like watch-only: review-only), and label it as such. Otherwise implement the LedgerXrpDevice sign-and-submit branch and add the golden field tests the design doc calls for.

XRW-28Trade-execution errors persisted to the local database without mapping

Informational CWE-532 / MASVS-STORAGE-2

Location. lib/data/database/tables.dart (TradeExecutions.lastError), lib/data/database/app_database.dart (updateTradeExecutionStatus(..., lastError:)), callers at trade_dashboard_screen.dart:254, 273, 290, 304.

Description. The new trade_executions table stores e.message, e.message?.toString(), and the PaymentOperationException.stage string into last_error. The Drift DB is the app's unencrypted "public metadata" store; allowBackup=false keeps it off cloud backup and off adb backup. The same dependency-exception analysis as XRW-25/26 applies, so no secret is written today — but raw, unmapped library text is now retained at rest, which is exactly what the wider remediation set out to stop.

Recommendation. Persist a small mapped enum (stage / error category) rather than free text; keep raw strings out of the row.

XRW-29Trade sign flow omits network fee and reserve impact from the review

Informational design-parity

Location. _OfferReviewDialog, lib/ui/trade/trade_dashboard_screen.dart:539–588.

Description. The autofilled fee is bounded — _signAndSubmit runs PaymentValidators.validateFeeDrops against AppConfig.maxFeeDrops (0.1 XRP) and throws before signing if exceeded — so there is no uncapped-fee exposure. But unlike the Send flow's reviewed-fee guard, the offer review dialog shows only the sell and buy amounts. It does not surface the actual fee, the XRP reserve increase from a resting offer, or a concrete "funds locked until filled/cancelled" figure. The feature's design document (§ "Review and Safety Rules") lists fee and reserve effect as mandatory review content.

Recommendation. Autofill (or estimate) before showing the review, and display fee + reserve delta there, matching Send.

XRW-31Trade-execution row written before the PIN is verified

Informational data hygiene

Location. trade_dashboard_screen.dart:160–185 (insert) vs. line 187 (promptAndVerifyWalletPin).

Description. _createLimitOrder inserts the trade_executions row with status: 'awaiting_approval' before prompting for the PIN. If the user cancels or fails the PIN, the row is left behind. Neither awaiting_approval nor submitted is in the terminal set used by getActiveTradeExecutions() (completed / cancelled / failed), so orphaned drafts accumulate in the "active" list.

Recommendation. Insert only after the PIN succeeds, or mark the row cancelled on abort; and make sure a successfully submitted order eventually reconciles to a terminal state.

Non-security observations

  • No tests for the Trade feature. There is no coverage of OfferCreate / OfferCancel field construction, AccountOffer parsing, result-code mapping, _toAmount drops conversion, or the v4 migration. AGENTS.md ("golden addresses / known vectors", "run flutter test before claiming crypto or import work is done") and the feature's own design document (Phase 1/2: "tests for offer parsing, cancellation construction, and result mapping"; "golden transaction-field tests") both call for them. Current suite: flutter analyze clean, flutter test 168/168.
  • Schema v3 → v4. Migration adds tradeExecutions and tradeExecutionSteps via createTable in the from < 4 branch; app_database.g.dart is regenerated consistently. No migration round-trip test was added (nor exists for v2/v3).
  • Stale in-app version string. lib/ui/settings/settings_screen.dart still shows "Version 1.0.1" in the About tile; pubspec.yaml is 2.0.0+4.
  • Per-network wallet filtering. WalletListController.reload() now filters wallets to the active network before ensureUniqueAddress and watcher sync. Importing the same address under both networks is therefore no longer de-duplicated. Likely intended (per-network wallets); worth an explicit decision and a test.
  • url_launcher adds a WebView activity. The manifest now contains a non-exported io.flutter.plugins.urllauncher.WebViewActivity. Current call sites use LaunchMode.externalApplication only; keep it that way so no in-app WebView is ever instantiated.
  • Android 16 local-network attribution. On the test device the OS lists android.permission.ACCESS_LOCAL_NETWORK as pre-granted (it is not in the app's declared list). With custom-endpoint support a user could point RPC/WSS at a LAN host. Low risk; noted only.
  • Test wiring warning. test/widget_test.dart logs a Drift "created the database class AppDatabase multiple times" warning. Non-fatal; test-only.
  • Per-offer PIN prompts in "Cancel all". _cancelAll loops _cancel, which prompts for the PIN each iteration — N dialogs for N offers. UX, not security.

Limitations

Live offer placement with real funds, Ledger USB signing, biometric unlock, the FGS watcher, and full create/import/backup flows on this build were not exercised. Device checks were run on a fresh install; the app's data was cleared and the process force-stopped afterwards, and the build was left installed on the device.
