Abstract

This pass follows the OWASP Mobile Audit project’s Android APK homologation layout rather than a free-form source review. The scanner (mpast/mobileAudit) decompiles an APK, extracts metadata, runs a CWE-mapped pattern engine, and records best practices. Those same sections were applied here to both the current tree (9a743c1) and the release APK installed on the connected Pixel 8 Pro, then extended with a wallet-specific reading of derivation, PIN, Keystore, payments, and the address-only watcher — areas a regex engine cannot judge.

No Critical findings. One High finding remains open and was re-confirmed on the installed binary: the release APK is still signed CN=Android Debug (XRW-01). Source now has an upload-keystore path for Play App Bundles, but it fail-opens to the debug key when android/key.properties is missing, and the APK on the device was not rebuilt with the upload cert. Two new Low findings (Ledger USB Java Log.i in release; no tap-filter on PIN/send) and three Informational items (PIN throttle, PIN-as-lock, un-obfuscated Dart snapshot) complete the open list.

Packaging controls that Mobile Audit treats as High when inverted are in the good state on this APK: allowBackup="false", debuggable unset, watcher service and plugin receivers exported="false", no cleartext, no WebView, no SMS / location / contacts. FLAG_SECURE on the PIN surface still blacks out adb screencap.

Methodology

Standard: OWASP Mobile Audit (Django SAST / malware APK scanner). Pattern IDs and CWE / Mobile Top 10 2016 mappings are taken from the project’s app/fixtures/data.json (patterns P2–P41, P100–P132, best-practice P200–P210). MASVS v2 control groups are listed alongside because that is the current OWASP MAS requirement language; Mobile Audit itself still maps to the 2016 Mobile Top 10.

Work performed:

  • Source review of lib/, android/app/, packages/ledger_usb_plus/
  • Merged-manifest / permission / certificate dump of the installed APK
  • Pattern-engine pass over Dart, Kotlin, Java, and XML (triaged)
  • Dynamic checks on Pixel 8 Pro (husky, Android 17 / API 37): signing, backup, exported components, FLAG_SECURE, logcat, run-as

Severity scale matches the 03 September report (Critical / High / Medium / Low / Informational). SAST hits that are expected for a local-first wallet (HTTPS JSON-RPC, SharedPreferences for public prefs, launcher exported=true) are triaged as false positives rather than opened as XRW items.

Prior report: 2026-09-03-security-audit-report.html. This document is a new audit, not an errata sheet.

Strings, databases, files

Strings in the APK

strings on the pulled APK found no PEM private keys, AWS/Stripe live tokens, or embedded mnemonics. Public RPC hosts and Dart storage key names are in libapp.so (XRW-23). Entropy domain string xrpl-mobile-wallet/v1/entropy is visible; that is a domain-separation label, not a secret.

Databases

Drift SQLite xrpl_wallet.sqlite in app documents: wallet rows (id, label, address, kind, network, Ledger flags), balances, cached txs. No mnemonic / seed / PIN columns. Auto Backup is off, so this file is not sent to Google Drive. A rooted device or debug-signed upgrade (XRW-01) can still read addresses and labels in the clear — that matches the local-first model (ledger data is public).

Files

  • Watcher address book JSON: public addresses + network + WSS host.

  • key.properties and *.jks / *.keystore are gitignored and not in the APK.

Wallet-specific source review

Mobile Audit’s regex engine does not understand XRPL derivation or a Flutter lock gate. This section is the complementary reading.

Derivation and entropy

New wallets draw 32 bytes from Random.secure. EntropyMixer.mix domain-separates xrpl-mobile-wallet/v1/entropy and SHA-256-mixes OS bytes with the dice/word ritual; the ritual cannot replace OS entropy. BIP39 path is m/44'/144'/0'/0/0 secp256k1 (matches xrpl.js Wallet.fromMnemonic). Create delegates to import. Family seeds use XRPPrivateKey.fromSeed on a separate path. Signing tries secp first and falls back to ed25519 only when expectedAddress matches a legacy mis-import.

Goldens still pin abandon×11+about and the genesis family seed. No new finding.

PIN, biometrics, auto-lock

PBKDF2-SHA256, 120k iterations, 16-byte salt; constant-time compare; legacy SHA-256 upgrades on success. Game PIN must differ. Spend, TrustSet, wipe, delete, and enabling biometrics re-prompt the wallet PIN. Biometrics are biometricOnly: true; the enabled flag is SharedPreferences and does not unwrap Keystore. Auto-lock is 90s after paused or inactive (USB permission dialogs can therefore lock an in-flight Ledger send). Failed-attempt counter is in-memory (XRW-02). PIN is not a KEK (XRW-19).

Payments

Review stores the fee; sign refuses unless autoFill matches (expectedFeeDrops) and stays under 0.1 XRP. Destination policy covers lsfRequireDestTag / lsfDisallowXRP including preset/coffee. Spendable check is amount+fee, with 1 XRP if the destination is unfunded. Secrets are read at the call site and the local reference is nulled in finally (Dart cannot wipe immutable strings; this is hygiene, not encryption). Ledger path compares device address to the wallet row and signs the STObject blob, not STX\\0.

Watcher isolate

watcherOnStart does not import KeyVault or PinService. Status notifications show host only. Activity notifications accept frames unless validated == false (omitted flag is treated as validated). A user-chosen malicious WSS can therefore spoof alerts and the USD cache; it cannot sign. Same trust as the selected RPC node.

Screen security

Refcounted FLAG_SECURE on create, import, attach-keys, send, unlock, setup PIN, and PIN/password dialogs. Wallet list, receive QR, and activity are not covered — addresses and balances are on-ledger public. Autofill is opted out of PIN fields.

XRW-01 Release APK signed with the shared Android debug key

High

Description. android/app/build.gradle.kts now reads android/key.properties when present (Play upload keystore) and otherwise assigns the debug signing config to release so flutter run --release still works. That fail-open is how a “release” APK becomes CN=Android Debug. Anyone who can induce the user to install a same-signature APK gets in-place access to Keystore entries and SQLite for this applicationId.

Impact. Full software-wallet key theft on that device after a malicious “update”. Ledger-only wallets are not drained this way (keys stay on the device), but watch metadata and custom endpoint URLs are inherited. Play App Signing cannot upgrade these installs in place (different cert, same id) — documented in README, still true for every debug-signed sideload currently in the field. 

buildTypes {
    release {
        signingConfig = if (keystorePropertiesFile.exists()) {
            signingConfigs.getByName("release")
        } else {
            signingConfigs.getByName("debug")
        }
    }
}

Device verification (Pixel 8 Pro, 05 Sep 2026). Pulled base.apk from /data/app/…/info.richlist.wallet-…/. apksigner: v2, DN C=US, O=Android, CN=Android Debug, SHA-256 4f7c44…8951 (same digest as 03 Sep). PackageManager signatures=[206b800e]. Tree app-release.apk (21:54, 03 Sep) matches. HEAD 9a743c1 landed 22:37 the same day and was never installed.

Resolution. Build and sideload an APK (or AAB) signed with the upload keystore; confirm apksigner verify --print-certs is no longer CN=Android Debug. Existing debug-signed installs need uninstall or a dual-signed migration APK. For CI / GitHub APKs, fail the release task when key.properties is missing instead of silently using debug.

XRW-21 Ledger USB Java plugin logs session details at INFO in release

Low

Description. XRW-10 closed Dart APDU hex dumps behind kDebugMode. The vendored packages/ledger_usb_plus Java still calls Log.i("LedgerUSB", …) on open, permission, and every exchangeApdu: device name, VID/PID, interface/endpoint numbers, APDU length, HID channel, transfer sizes. Confirmed on device at process start (no Ledger attached): 

I LedgerUSB: LedgerManager singleton created
I LedgerUSB: plugin attached to engine, manager connected=false
I LedgerUSB: plugin attached to activity MainActivity

Impact. Not key material. A logcat reader learns that a Ledger session is happening and the size of APDUs. Payloads are not printed. Mobile Audit P17 / CWE-532 still counts INFO logs of transport metadata on a wallet as a Low.

Resolution. Gate the Java logger on BuildConfig.DEBUG (or a verbose flag), matching the Dart side.

XRW-22 PIN and send confirm do not filter obscured touches

Low

Description. Mobile Audit P210 / CWE-1021 expects setFilterTouchesWhenObscured(true) (or onFilterTouchEventForSecurity) on authentication and payment confirmation. MainActivity never sets it. The app does not use TYPE_SYSTEM_ALERT or overlay APIs itself (P36 clean).

Impact. On older overlay-capable builds, another app with SYSTEM_ALERT_WINDOW could sit over the PIN pad or the Sign button. Android 12+ tightened overlays; this is not remotely exploitable. Still a gap versus the Mobile Audit best-practice list for a wallet.

Resolution. Set filter-touches-when-obscured on the activity (or the PIN / send widgets) and add a widget test or a comment pointing at the flag.

XRW-02 No persistent PIN throttling

Informational

Description. Failed unlock attempts live in UnlockScreen._failedAttempts. The counter is in-memory, resets after the third failure when the Zerpland decoy opens (no game PIN), and does not survive process death. Minimum PIN length is 6 digits.

Impact. Online guessing of a 6-digit space on unlocked hardware has no durable delay. Product mitigation is the 3-fail decoy and the optional game PIN. The PIN hash is not a KEK (XRW-19): an attacker who can read Keystore already has the seeds. Maintainer accepted this previously; it is unchanged.

XRW-19 PIN is an application lock, not a KEK

Informational

Description. kAppSecureStorage uses AndroidOptions(resetOnError: false) with plugin 10.3.1 defaults: RSA-OAEP wrap, AES-GCM storage. The PIN verifier is PBKDF2-SHA256; it is not used to wrap wallet_secret_*. Hardware-backed setUserAuthenticationRequired / AndroidOptions.biometric() is not enabled.

Impact. Correct for the current threat model, and easy to misread after the KDF upgrade. A compromised UI process, or Keystore access on an unlocked device, does not need the PIN. Binding vault keys to user authentication is a product decision, not a defect in the current split.

XRW-23 Dart snapshot not obfuscated; storage key names in libapp.so

Informational

Description. Release was not built with flutter build apk --obfuscate --split-debug-info=…. lib/arm64-v8a/libapp.so in the installed APK contains wallet_secret_, app_pin_hash, game_pin_hash, and the entropy domain string. Java/Kotlin R8 minify is on (Flutter plugin default).

Impact. MASVS-RESILIENCE-3 / M9. Key values are not in the package. Names only help an attacker who already has app-data or a debugger choose which Keystore aliases to dump. OWASP states that missing resilience controls are not themselves a vulnerability. Listed so a later hardening pass can add --obfuscate without rediscovering it.

Limitations

  • VirusTotal / MalwareDB / Maltrail integrations from the Mobile Audit product were not run (no APK upload to those services).
  • No USB Ledger was attached, so APDU exchange and on-device fee display were not live-tested. Java INFO logs were confirmed at plugin attach only.
  • No mainnet/testnet payment was submitted; fee-match and spendable checks remain unit-tested.
  • No second-party APK was built to demonstrate the debug-key upgrade attack end-to-end; cert identity plus prior successful adb install -r of a same-signature rebuild is the evidence.
  • iOS was out of scope.
