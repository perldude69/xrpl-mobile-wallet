Findings

XRW-24Recovery phrase can be copied to the system clipboard

Low CWE-312 / MASVS-STORAGE-2

Location. lib/ui/wallets/create/create_wallet_screen.dart (_copyPhrase(), backup step of wallet creation).

Description. The "copy" affordance on the 24-word recovery-phrase backup step places the full phrase in the system clipboard via Clipboard.setData. The app shows a warning snackbar and, after 60 seconds, clears the clipboard — but only if the clipboard still contains the exact phrase.

Impact. The clipboard is a system-wide channel: on Android ≤ 9 any focused app can read it, and keyboard / clipboard manager apps (e.g. cloud-synced keyboards) may persist or sync its contents beyond the 60-second window. A leaked phrase is total loss of funds for the wallet. User action is required (tapping copy), which is why this is Low and not Medium.

Existing mitigations. Explicit "clipboard is not secure" warning; conditional auto-clear after 60 s; Android 12+ system toast on clipboard access; FLAG_SECURE blocks screen capture of the surface itself.

Recommendation. Prefer transcription-only UX (the phrase grid + verification quiz already exist). If copy stays: copy per word or in short chunks instead of the whole phrase, shorten the auto-clear to the next user action, and label the affordance as discouraged. Note addresses and tx hashes are also copied elsewhere, but those are public data and not part of this finding.

XRW-25Raw exception text passed through to user-visible errors

Informational CWE-209 / MASVS-CODE

Location. Several UI error paths render e.toString() from raw library exceptions, e.g. lib/ui/send/send_screen.dart (destination-policy / submission paths), lib/ui/wallets/import/import_screen.dart and lib/ui/wallets/attach_keys/attach_keys_entry_screen.dart (non-ArgumentError catch), and lib/ui/settings/backup_settings.dart ('Export failed: $e').

Description. Exceptions from dependency code are converted into on-screen error text without mapping. An audit of the crypto dependencies actually invoked with secret-bearing input found their exception texts are fixed strings (blockchain_utils throws MnemonicException("Invalid mnemonic checksum."), "Invalid mnemonic length.", etc. — never quoting the phrase), so no secret leakage exists today. The risk is that a future dependency update could introduce richer exception messages (or an exception carrying user input) that would then surface verbatim on screen — including on surfaces that may not be FLAG_SECURE-protected (e.g. the send flow).

Recommendation. Map exceptions to fixed, short user-facing messages at the state/controller boundary and keep the raw error out of widget state. A single helper (friendlyError(Object e)) with allow-listed messages plus a generic fallback ("Something went wrong; try again") would close the channel for all listed sites.
